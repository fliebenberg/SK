### Organisation Membership & Profiles

- [ ] `MEMBER-1` **There is no way to join an organisation other than an admin adding you.** `org_memberships` rows are written by admin screens and by the claim flow; nothing models a person asking to join, and an organisation cannot say whether it accepts requests at all. **Decided 2026-09-03 — two modes, per organisation.** `invite` (the default): only an org admin creates a membership. `apply`: anybody may apply, and **applying does not make them a member** — the application sits pending until an org admin approves it, at which point the membership row is written. An admin can switch the org between the two. Needs: a mode on `organizations` (defaulting to `invite`, so existing orgs are unchanged), an application record with a pending / approved / declined state, the two actions to apply and to decide, notification to the org's admins, and a screen for the queue. Related: `PEOPLE-2` gates who may create a profile in the first place — the two are the same principle at two levels, since an approved application is what turns a person into a member rather than merely a profile. Logged rather than built because it does not touch the tournament work; raised 2026-09-03 during tournaments Phase 4.

- [ ] `MEMBER-2` **A person who belongs to no organisation has nowhere to be recorded.** `org_profiles` is per-org by design (`UNIQUE (org_id, identifier)`, the org's own name and number for that person), so somebody who is on the app but affiliated to nobody — an external official, a parent, a person who signed up through an invite and joined nothing — can only be recorded inside whichever org happened to touch them first. That org then owns their only person-record indefinitely, which is contrived in the general case. **Decided 2026-09-03 — a reserved organisation as a membership-free home for person records, under three constraints**, each of which is the difference between this being useful and being a privacy hole:
  - **Nothing ever writes an `org_memberships` row against it.** A membership row *is* a permission in this codebase: `getMembershipSnapshot` counts any current one, so "every user is a member of the global org" would hand everyone `org:{id}:members`, every team roster the org can see, and — since `isOrgMember` now selects the full search projection — everyone's `cellphone`, `birthdate` and `national_id`.   - **It is excluded from the organisation directory and from member-scoped search**, for the same reason.
  - **It does not replace per-org profiles.** A person still needs a profile at their school to be a player there; the reserved-org row is the "not affiliated with anyone yet" record, not a canonical one. `AccessManager` already resolves a user into a *set* of profile ids, so several rows per human is the existing model rather than a new problem.
